# Ifverse from ChatGPT — Chrome on Windows

This is the new hosted path; it supersedes the desktop/loopback setup in SOCIAL_PUBLISHING for ChatGPT use. **Deployment, Sites entitlement, provider consent and live account ownership are not verified. No public post is authorized by this implementation.** The existing YouTube alias is an intended destination, not an owner OAuth grant. No Instagram, Facebook or TikTok binding has been invented.

The checked-in entry point is `sites/server.mjs` (MCP over Streamable HTTP), calling `whatif.publishing_api`. Durable state lives on one private persistent volume, never in GitHub caches, build artifacts, the Sites filesystem or this chat. This runs without the owner's PC. API and MCP ingress require independent bearer credentials entered in host settings. Do not paste credentials into ChatGPT.

## Chrome checklist: one-time backend and plugin enablement

1. In Chrome open the private [repository](https://github.com/Vpermillion/Content_Creating_WorkFlow). Review `codex/ifverse-chatgpt-publishing` against `codex/chrome-publishing-inventory` (PR #3's head). Do not merge into the old portable branch. Read deployment constraints below before creating a service.
2. On an existing container host supporting a private GitHub repository, HTTPS and a **persistent disk**, deploy `deploy/Dockerfile.publishing` from this branch. A concrete browser path on [Render](https://dashboard.render.com/) is **New + → Web Service → Git Provider → connect the private repository → Branch → codex/ifverse-chatgpt-publishing → Language/Runtime → Docker → Dockerfile Path → deploy/Dockerfile.publishing**. Under **Disks → Add Disk**, mount `/state`, owned by container UID 10001 with mode 0700. Use one instance/worker for this volume. Persistent disks may require a paid plan; no account creation, purchase or deployment was performed here. If that option is unavailable, use an already authorized host with equivalent disk and HTTPS controls; ephemeral/free web containers do not meet durability requirements.
3. Under the host's **Environment**, enter `IFVERSE_STATE=/state`, `IFVERSE_ROOT=/app`, `PORT=8080`, `IFVERSE_PUBLIC_ORIGIN=https://YOUR-BACKEND`, and strong independently generated `IFVERSE_API_TOKEN` and `IFVERSE_MEDIA_KEY` as secrets. Enter `IFVERSE_OAUTH_CONFIG` as a secret JSON object with `youtube`, `meta`, and/or `tiktok` entries. Each has `client_id` and `client_secret`; Meta also has `graph_version` set to the currently supported `vN.N` version. Values come directly from the provider dashboards, never chat. Deploy after entering them. Disable ingress/access/query logging, request-body capture and analytics for `/oauth/callback`, `/media/*`, and API requests. Keep TLS verification enabled.
4. Open [ChatGPT](https://chatgpt.com/) in Chrome. Check whether your account has **Sites** and **Plugin Creator**. In Plugin Creator, create an **owner-only** plugin using `sites/package.json`, `sites/package-lock.json`, and `sites/server.mjs` as server-runtime code. Install with `npm ci`; start with `npm start`; MCP path is `/mcp`. In Sites server settings enter `IFVERSE_BACKEND_URL`, `IFVERSE_API_TOKEN`, and an independent `IFVERSE_MCP_TOKEN`. Configure the plugin's MCP request authorization as `Authorization: Bearer` using that ingress secret. Keep visibility **owner only** and enable the plugin in a new chat. Do not expose these variables to client-side code.
5. Follow the current [Sites MCP guide](https://learn.chatgpt.com/docs/extend/mcp#use-a-sites-hosted-mcp-server-in-chatgpt) and [hosting guide](https://help.openai.com/en/articles/20001547-hosting-a-plugin-with-chatgpt-sites) for Plugin Creator registration. This workspace could not load those hosts (proxy 403); their current UI buttons/runtime contract and your entitlement are **not verified**. The checked-in server's protocol is tested, but Sites registration is not. If your Sites runtime cannot mount this Node server or attach its ingress authorization, stop at that integration boundary; do not make MCP anonymous. Adapt the server runtime/registration to the actual supported Sites interface first.
6. If Sites is absent, an arbitrary remote MCP write connector requires the supported **Business or Enterprise/Edu** path described in [custom MCP setup](https://help.openai.com/en/articles/12584461-connecting-custom-mcp-servers-in-chatgpt). Deploy the same wrapper behind authenticated ingress and register it only where authenticated write connectors are available. Personal Plus/Pro remote write entitlement is not assumed. Do not paste the backend bearer key into a normal chat message.
7. In a new chat invoke `ifverse_accounts`, then `ifverse_verify`. A registry listing is not a connected account. Make a test draft and retrieve its ID in another chat before granting any public posting approval. Store encrypted disk backups and test restoring drafts, grants and original upload sessions together. No real backup/restore was performed here.

The Render labels above are an explicit deployment recipe, not an observed deployment. Nothing in this checklist requires WSL, local Python, cloning on Windows or leaving Windows on.

## Callable contract and media reuse

`ifverse_media_prepare(request_id)` runs one existing `review-requests/ID.json` through `scripts/render_test_video.run`, preserving owner-topic/script checks, footage cache, narration, captions, editing and final-media receipts. Poll `ifverse_media_status`. Repeated calls return the original durable job and do not rerender. A crash leaves its job held for inspection. New free-form story intake still requires the existing script/shot-plan/topic-choice process; this change does not pretend the renderer can turn an arbitrary sentence into reviewed footage. No new production render was authorized or run during implementation.

Existing finished media can be ingested by the hosted producer with authenticated binary `POST /media`; it returns its SHA-256. This is a server-to-server integration, not a Windows task. Media preparation may be performed by the existing GitHub jobs; do not store actual private production media in Git or Actions artifacts. Keep provider grants off production runners unless that runner actually needs them. The container includes renderer dependencies; network/model access and real rendering on the deployed host remain unverified.

`ifverse_prepare(brand,destinations)` saves an immutable draft. Each destination has `account`, `format`, `title`, `caption`, `media_sha256` and the existing media job `manifest` containing at least `brand`, `episode`, `master_sha256`, `video_sha256`, and actual `review` evidence when ready. Account/platform IDs are taken from the registry, never caller-supplied overrides. Current topic master and actual media bytes are checked. Existing review gates run again before publishing; pending editorial/source-use/topic choice remains blocked. Do not fabricate an approved review to make a draft publishable.

`ifverse_preview(draft_id)` retrieves the exact saved destinations/captions, temporary media preview URLs, snapshot hash and per-destination status from any fresh session. Show those to the owner. Draft contents cannot be edited; prepare a new draft for changed captions/media. A second draft cannot bypass a reserved media-job/account publication operation.

`ifverse_publish(draft_id,snapshot_hash,destinations,approved=true)` is called only after the owner's explicit approval of the shown snapshot. “Post it” approves that exact clear draft/destination set; “Post it on Instagram only” selects only its Instagram alias. Ambiguous drafts or destinations require clarification. The trusted owner-only MCP caller carries the actual conversational approval; the backend cannot independently prove a phrase was spoken. Never equate preparation, a registry row or a technical test with approval.

Successful destinations are skipped permanently. Each provider call is preceded by durable intent; checkpoints survive failures. Grant expiry before a write yields `awaiting_consent`. Uncertain Meta writes yield `needs_reconciliation`; provider IDs are read back, a finished unposted container may be continued, but an uncertain `media_publish` is held rather than repeated. `submitted/processing` is not `published`. Confirmed public URLs are returned only with provider confirmation. TikTok Studio remains `action_required` until ownership verification. Ask for a retry of one destination and pass exactly that alias.

YouTube reuses `youtube_publish.upload`, saving the original private resumable session before chunks and probing that same session after uncertain completion. Lost initiation or unavailable sessions are held, never replaced with a fresh insert. See [official resumable protocol](https://developers.google.com/youtube/data/guides/using_resumable_upload_protocol). YouTube journals and OAuth tokens live only on the private volume. The historic local/GitHub social workers must not also process the same production account/job: choose this hosted path as its sole queue and reconcile/migrate old receipts first. Cross-queue state migration is not automatic.
