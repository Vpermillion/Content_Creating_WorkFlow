# Ifverse from ChatGPT — Chrome on Windows

This is the new hosted path; it supersedes the desktop/loopback setup in SOCIAL_PUBLISHING for ChatGPT use. **Deployment, Sites entitlement, provider consent and live account ownership are not verified. No public post is authorized by this implementation.** The existing YouTube alias is an intended destination, not an owner OAuth grant. No Instagram, Facebook or TikTok binding has been invented.

The checked-in Sites entry point is `sites/worker.mjs` (native stateless MCP), calling `whatif.publishing_api`. Durable state lives on one private persistent volume, never in GitHub caches, build artifacts, the Sites filesystem or this chat. This runs without the owner's PC. Sites authenticates the owner. The Sites Worker uses a server-side bearer credential for the publishing API. Do not paste credentials into ChatGPT.

## Chrome checklist: one-time backend and plugin enablement

1. In Chrome open the private [repository](https://github.com/Vpermillion/Content_Creating_WorkFlow). Review `codex/ifverse-chatgpt-publishing` against `codex/chrome-publishing-inventory` (PR #3's head). Do not merge into the old portable branch. Read deployment constraints below before creating a service.
2. On an existing container host supporting a private GitHub repository, HTTPS and a **persistent disk**, deploy `deploy/Dockerfile.publishing` from this branch. A concrete browser path on [Render](https://dashboard.render.com/) is **New + → Web Service → Git Provider → connect the private repository → Branch → codex/ifverse-chatgpt-publishing → Language/Runtime → Docker → Dockerfile Path → deploy/Dockerfile.publishing**. Under **Disks → Add Disk**, mount `/state`, with the service creating an owner-only `private` subdirectory at startup. Use one instance/worker for this volume. Persistent disks may require a paid plan; no account creation, purchase or deployment was performed here. If that option is unavailable, use an already authorized host with equivalent disk and HTTPS controls; ephemeral/free web containers do not meet durability requirements.
3. Under the host's **Environment**, enter `IFVERSE_STATE=/state/private`, `IFVERSE_ROOT=/app`, `PORT=8080`, `IFVERSE_PUBLIC_ORIGIN=https://YOUR-BACKEND`, and strong independently generated `IFVERSE_API_TOKEN` and `IFVERSE_MEDIA_KEY` as secrets. Set a separate `IFVERSE_OWNER_PASSWORD` of at least 32 characters for the TikTok browser forms. Enter `IFVERSE_OAUTH_CONFIG` as a secret JSON object with `youtube`, `meta`, and/or `tiktok` entries. Each has `client_id` and `client_secret`; Meta also has `graph_version` set to a supported `vN.N` version. If using a Facebook Login for Business configuration, set its ID as `login_config_id`. Values come directly from the provider dashboards, never chat. Deploy after entering them. Disable ingress/access/query logging, request-body capture and analytics for `/oauth/callback`, `/media/*`, and API requests. Keep TLS verification enabled.
4. In [ChatGPT Work](https://chatgpt.com/), install **Plugin Creator** from **Plugins** if needed. Open a Work chat with **@Plugin Creator** and give it the checked-in `sites` folder. Ask it to deploy the native MCP Worker as an owner-only Site, keeping the `mcp` capability. The build command is `npm run build`. Sites assigns the project ID and generates the private plugin.
5. In **Sites → More actions → Settings**, enter `IFVERSE_BACKEND_URL` with the HTTPS service origin, `IFVERSE_BACKEND_TOKEN` with the backend’s `IFVERSE_API_TOKEN`, and `IFVERSE_SITE_OWNER_EMAIL` with the owner’s verified ChatGPT email. Deploy privately. Choose **Install** or **Connect** from the plugin card or **Plugins → Personal → Created by you**. Select the plugin with `@` in a fresh Work chat. [Sites MCP setup](https://learn.chatgpt.com/docs/extend/mcp#use-a-sites-hosted-mcp-server-in-chatgpt) · [Runtime settings](https://learn.chatgpt.com/docs/sites/managing-a-site#configure-runtime-environment-values)
6. The separate `sites/server.mjs` provides a conventional MCP transport for hosts that supply authenticated ingress. ChatGPT custom remote writes require an eligible Business or Enterprise/Edu workspace and its supported MCP OAuth configuration. Use the native Sites path for a personal account with Sites access. [Custom MCP setup](https://help.openai.com/en/articles/12584461-connecting-custom-mcp-servers-in-chatgpt)
7. In a new chat invoke `ifverse_accounts`, then `ifverse_verify`. A registry listing is not a connected account. Make a test draft and retrieve its ID in another chat before granting any public posting approval. Store encrypted disk backups and test restoring drafts, grants and original upload sessions together. No real backup/restore was performed here.

The Render labels above are an explicit deployment recipe, not an observed deployment. Nothing in this checklist requires WSL, local Python, cloning on Windows or leaving Windows on.

## Callable contract and media reuse

`ifverse_media_prepare(request_id)` runs one existing `review-requests/ID.json` through `scripts/render_test_video.run`, preserving owner-topic/script checks, footage cache, narration, captions, editing and final-media receipts. Poll `ifverse_media_status`. Repeated calls return the original durable job and do not rerender. A crash leaves its job held for inspection. New free-form story intake still requires the existing script/shot-plan/topic-choice process; this change does not pretend the renderer can turn an arbitrary sentence into reviewed footage. No new production render was authorized or run during implementation.

For an existing render already recorded in the private GitHub topic registry, call `ifverse_media_import(brand,episode)`. It imports the MP4 at the recorded commit and checks its SHA-256. To enable this tool in Chrome, open [fine-grained GitHub tokens](https://github.com/settings/personal-access-tokens/new), select `Vpermillion` as resource owner and only `Content_Creating_WorkFlow`, grant **Repository permissions → Contents → Read-only**, and save the token directly as `IFVERSE_GITHUB_READ_TOKEN` in the host environment. For media stored outside the existing Git results, the hosted producer can send authenticated binary `POST /media` server to server. The container includes renderer dependencies; real rendering on the deployed host still needs verification.

`ifverse_prepare(brand,destinations)` saves an immutable draft. Each destination has `account`, `format`, `title`, `caption`, `media_sha256` and the existing media job `manifest` containing at least `brand`, `episode`, `master_sha256`, `video_sha256`, and actual `review` evidence when ready. Account/platform IDs are taken from the registry, never caller-supplied overrides. Current topic master and actual media bytes are checked. Existing review gates run again before publishing; pending editorial/source-use/topic choice remains blocked. Do not fabricate an approved review to make a draft publishable.

`ifverse_preview(draft_id)` retrieves the exact saved destinations/captions, temporary media preview URLs, snapshot hash and per-destination status from any fresh session. Show those to the owner. Draft contents cannot be edited; prepare a new draft for changed captions/media. A second draft cannot bypass a reserved media-job/account publication operation.

`ifverse_publish(draft_id,snapshot_hash,destinations,approved=true)` is called only after the owner's explicit approval of the shown snapshot. “Post it” approves that exact clear draft/destination set; “Post it on Instagram only” selects only its Instagram alias. Ambiguous drafts or destinations require clarification. The trusted owner-only MCP caller carries the actual conversational approval; the backend cannot independently prove a phrase was spoken. Never equate preparation, a registry row or a technical test with approval.

Successful destinations are skipped permanently. Each provider call is preceded by durable intent; checkpoints survive failures. Grant expiry before a write yields `awaiting_consent`. Uncertain Meta writes yield `needs_reconciliation`; provider IDs are read back, a finished unposted container may be continued, but an uncertain `media_publish` is held rather than repeated. `submitted/processing` is not `published`. Confirmed public URLs are returned only with provider confirmation. TikTok Studio remains `action_required` until browser or Display API verification. Ask for a retry of one destination and pass exactly that alias.

YouTube reuses `youtube_publish.upload`, saving the original private resumable session before chunks and probing that same session after uncertain completion. Lost initiation or unavailable sessions are held, never replaced with a fresh insert. See [official resumable protocol](https://developers.google.com/youtube/data/guides/using_resumable_upload_protocol). YouTube journals and OAuth tokens live only on the private volume. The historic local/GitHub social workers must not also process the same production account/job: choose this hosted path as its sole queue and reconcile/migrate old receipts first. Cross-queue state migration is not automatic.
